# 小说SOP最终流程

这份文件是 `aiReading` 的唯一小说 SOP 流程入口。

日常写章、修章、验收、交付和交给其他模型接管时，默认只读这份文件，再按需读取它明确指定的最小材料。

## 一、核心原则

1. 规则只放一处：硬性字数、标题、排版、内容边界和上下文预算，以 `当前有效规则卡.md` 为准。
2. skill 默认短卡化：日常只读 `SOP资料/skills/技能短卡.md` 中本章需要的 1-2 个摘要。
3. workflow 不日常陪跑：非 AI 专项只保留短卡，不再保留完整 skill / workflow 作为日常资料。
4. 三卡只维护，一包只投喂：不要把上下文包和三张源卡同时塞给模型。
5. 先验 txt，再交付 docx：正文先以 `.txt` 起草、修订、初验，通过后再渲染 `.docx`。
6. 不使用外部记忆层或终端压缩工具；故事事实、执行口和流程判断只以项目文件为准。

## 二、保留的有效入口

日常有效入口只保留这些：

- `小说SOP最终流程.md`：唯一流程说明。
- `当前有效规则卡.md`：唯一硬规则源。
- `SOP资料/skills/技能短卡.md`：日常 skill 摘要入口。
- `小说框架/09_当前卷执行状态卡_模板.md`：状态卡模板。
- `小说框架/10_当前章任务卡_模板.md`：任务卡模板。
- `小说框架/12_状态卡维护规则.md`：状态卡维护细则。
- `scripts/prepare_chapter_context.py`：生成当前章上下文包。
- `scripts/audit_context_budget.py`：审计上下文预算。
- `scripts/check_task_card.py`：检查任务卡。
- `scripts/compress_state_card.py`：输出状态卡压缩建议。
- `scripts/lint_sop_references.py`：检查 SOP 是否重新出现重复规则或错误默认读取。
- `scripts/run_chapter_acceptance.py`：章节验收。
- `scripts/run_chapter_pipeline.py`：通过初验后渲染 docx 并做最终流水线。

专项保留：

- `SOP资料/workflows/去AI味修订工作流模板.md`
- `SOP资料/skills/去AI味修订/SKILL.md`

这两份只在用户明确要求专项处理生成味，或当前章结构已成立但文面明显需要专项修订时打开。

## 三、默认不读

日常写章默认不读：

- `开书输入.md`
- `小说框架/03_总目录.md`
- `小说框架/06_卷划分.md`
- `小说框架/07_人物小传.md`
- `进度记录.md`
- `章节验收记录.md`
- `归档/`
- 完整 skill
- 完整 workflow
- 多章正文

只有出现以下情况才扩容：

1. 当前章任务卡缺失或明显不可靠。
2. 当前卷状态卡出现冲突。
3. 连续性疑似写乱。
4. 要重排整卷或改总目录。
5. 要批量回修多章。
6. 自动验收结果疑似误报。

扩容完成后，必须把稳定结论压回状态卡和任务卡，再回到最小流程。

## 四、开书初始化

开新书时只做一次初始化。

默认输入：

1. `开书输入.md`
2. `当前有效规则卡.md`
3. `小说框架/09_当前卷执行状态卡_模板.md`
4. `小说框架/10_当前章任务卡_模板.md`

默认产出：

1. `小说框架/00_作品定位.md`
2. `小说框架/01_世界观与主线.md`
3. `小说框架/02_人物关系表.md`
4. `小说框架/03_总目录.md`
5. `小说框架/04_节奏设计.md`
6. `小说框架/05_作品简介.md`
7. `小说框架/06_卷划分.md`
8. `小说框架/07_人物小传.md`
9. 第一卷执行状态卡
10. 第 1 章任务卡

初始化完成后，`开书输入.md` 退回输入源，不再进入每章默认上下文。

## 五、三卡一包双日志

三卡：

1. `当前有效规则卡.md`
2. 当前卷执行状态卡
3. 当前章任务卡

一包：

1. `当前章上下文包.md`

双日志：

1. `进度记录.md`
2. `章节验收记录.md`

三卡是源文件，一包是投喂结果。双日志只做留痕，不进日常上下文。

## 六、当前卷状态卡规则

状态卡只写当前卷仍然有效的结果，不写过程。

必须遵守：

- 每栏最多 4 条。
- 单条建议不超过 80 字，最长不超过 120 字。
- 每条事实带 `[源：第X章]`。
- 推断写 `[推断：基于第X章]`。
- 不按章节逐条追加摘要。
- 已失效事实立刻删除或归档。
- 卷结束后新卷重开一张，不把上一卷长卡原样续写。

状态卡压缩建议：

```bash
python3 scripts/compress_state_card.py 小说框架/第一卷执行状态卡.md
```

## 七、当前章任务卡规则

任务卡只服务当前这一章，不写原因解释，不写剧情复述。

固定栏目：

1. `本章只办成`
2. `必须承接`
3. `本章禁写`
4. `章尾结果`
5. `建议技能`
6. `写完后回填`

必须遵守：

- `本章只办成` 最多 3 条。
- 其他栏目最多 4 条。
- 单条建议不超过 80 字，最长不超过 120 字。
- 用命令式短条。
- 避免“因为 / 所以 / 意味着 / 体现 / 铺垫”等解释腔。
- 写完后只保留下一章还真的要继续用的内容。

任务卡检查：

```bash
python3 scripts/check_task_card.py 小说框架/当前章任务卡.md
```

## 八、生成当前章上下文包

每章开工前生成最小上下文包：

```bash
python3 scripts/prepare_chapter_context.py \
  --volume-card 小说框架/第一卷执行状态卡.md \
  --task-card 小说框架/当前章任务卡.md \
  --output 小说框架/当前章上下文包.md
```

默认预算：

- `当前章上下文包.md` 不超过 4000 字。
- `当前有效规则卡.md` 不超过 1600 字。
- 当前卷状态卡不超过 1800 字。
- 当前章任务卡不超过 1200 字。

审计预算：

```bash
python3 scripts/audit_context_budget.py \
  --volume-card 小说框架/第一卷执行状态卡.md \
  --task-card 小说框架/当前章任务卡.md \
  --context-pack 小说框架/当前章上下文包.md
```

给模型时默认只给：

1. `当前章上下文包.md`
2. 当前待写 / 待修正文
3. 必要时前 1 章正文；承接复杂时最多前 2 章

不要再额外附送三张源卡原文。

## 九、单章执行流程

1. 维护当前卷状态卡和当前章任务卡。
2. 生成 `当前章上下文包.md`。
3. 检查脚本输出的分段长度。
4. 给模型时只传上下文包、当前正文和必要前章。
5. 起草或修正文，优先落成 `.txt` 源稿。
6. 逐句通读，修错字、病句和语感问题。
7. 先验 `.txt`。
8. 不通过就修 `.txt`。
9. 通过后再渲染 `.docx`。
10. 需要最终交付时跑流水线。
11. 只把仍然有效的结果回填状态卡、任务卡和短日志。

草稿初验：

```bash
python3 scripts/run_chapter_acceptance.py --chapter 小说正文/源稿/001_章节名.txt
```

最终交付流水线：

```bash
python3 scripts/run_chapter_pipeline.py --input 小说正文/源稿/001_章节名.txt
```

如果确实需要对照总目录或更多正文，必须显式传参：

```bash
python3 scripts/run_chapter_acceptance.py \
  --chapter 小说正文/源稿/001_章节名.txt \
  --outline 小说框架/03_总目录.md \
  --previous-dir 小说正文
```

## 十、验收规则

默认验收基准：

1. 当前章任务卡
2. 当前卷状态卡
3. 当前有效规则卡

默认不对照总目录。总目录只在任务卡缺失、任务卡明显不可靠或章节推进错位时读取。

验收只输出三档：

- `通过`：可以进入下一章。
- `警告`：可继续，但风险必须回填状态卡或任务卡。
- `不通过`：先修阻塞问题，再重新验收。

## 十一、日志规则

`进度记录.md` 和 `章节验收记录.md` 只写短记录。

不要写：

- 长段剧情总结。
- 本章意义分析。
- 多次重复验收的完整旧结果。
- 已经写入状态卡或任务卡的事实复述。

同一章重复跑流程时，活跃日志只保留最新结果，旧记录转入 `归档/`。

## 十二、SOP 自检

改动 SOP 后运行：

```bash
python3 scripts/lint_sop_references.py --root .
```

这条检查必须通过，防止重新出现：

- 把总目录设为日常材料。
- 把进度记录或验收记录设为日常材料。
- 把完整 skill 设为日常材料。
- 上下文包和三张源卡并列投喂。
- 硬性字数、标题、排版规则散落到多个文件。

## 十三、一句话总结

`aiReading` 的日常写章不靠更多上下文，而靠分层和去重：

规划层负责规划，规则卡负责硬规则，状态卡负责当前事实，任务卡负责当前章执行口，上下文包负责投喂，日志负责追溯。
