# 小说写作总控skill

这个skill不替代其他6个skill，而是负责决定：
- 当前任务属于哪一层写作问题
- 应该优先调用哪几个基础skill
- 多个skill之间的先后顺序是什么
- 最终输出时，如何保证正文统一

## 统辖的6个基础skill

1. 正文语言风格
2. 场景描写
3. 情绪动作表达
4. 人物专属动作签名
5. 人物专属台词签名
6. 人物关系对话

## 辅助验收skill

- 章节验收与连续性校验：用于章节完成后检查硬规则、推进度、连续性、重复回退风险。

它不替代上面的 6 个基础写作 skill，只负责在章节完成后做验收。

## 总控原则

- 不能为了凑字数而凑字数。
- 不能通过重复段落、重复表意、同义反复硬拉字数。

- 先判断问题层级，再下手修改。
- 先修结构性错误，再修文笔性问题。
- 先保证人物和关系成立，再追求漂亮句子。
- 任何局部优化都不能破坏全文统一性。

## 本skill的SOP流程

1. 先判断当前任务属于：创作、修订、统一文风、人物校准、对白校准、关系修订中的哪一类。
2. 判断当前问题是结构优先，还是文笔优先；默认先修结构。
3. 从6个基础skill里选出1个主skill和1到3个辅skill，不要平均调用。
4. 按“先结构、再场景人物、后语言统一”的顺序执行。
5. 最终必须回到“正文语言风格”做全文收束。
6. 若章节已经成稿或准备交付，补做“章节验收与连续性校验”。
7. 如果任务较大，优先引导进入对应 workflow，而不是直接乱修正文。

## 使用流程

### 场景一：用户让你“直接写正文”
按这个顺序处理：
1. 用“正文语言风格”定叙述基线。
2. 用“人物专属动作签名”和“人物专属台词签名”校准角色。
3. 用“场景描写”搭建环境。
4. 用“情绪动作表达”把情绪落地。
5. 用“人物关系对话”修对话温度与边界。

### 场景二：用户说“这段像流水账”
优先调用：
1. 正文语言风格
2. 场景描写
3. 情绪动作表达

### 场景三：用户说“人物写得不像一个活人”
优先调用：
1. 人物专属动作签名
2. 人物专属台词签名
3. 人物关系对话

### 场景四：用户说“对白都一个味儿”
优先调用：
1. 人物专属台词签名
2. 人物关系对话
3. 情绪动作表达

### 场景五：用户说“这一章没气氛”
优先调用：
1. 场景描写
2. 正文语言风格
3. 情绪动作表达

## 调用流程示例

### 示例一：从提纲到正文
适用场景：用户给出一段大纲，希望扩写成小说正文。

调用顺序：
1. 正文语言风格：把“大纲信息”转成“场景化叙述基线”。
2. 场景描写：决定这一场主要空间压力与画面锚点。
3. 人物专属动作签名：让主要人物在动作上不串味。
4. 人物专属台词签名：让人物开口时像自己。
5. 情绪动作表达：把情绪落在动作与停顿里。
6. 人物关系对话：校准对话里的权力、亲疏和潜台词。
7. 回到正文语言风格：统一收束整段文字，删掉提纲腔。

### 示例二：修“像流水账”的章节
适用场景：已有正文，但读起来像在汇报剧情。

调用顺序：
1. 正文语言风格：先找出摘要句、解释句、重复句。
2. 场景描写：补足空间、物件、温度、声音，让段落落地。
3. 情绪动作表达：把“她很难过”之类的句子改成动作化表达。
4. 人物关系对话：检查对话是否只在传信息，没有关系温度。
5. 正文语言风格：做最终统一，保证章节节奏。

### 示例三：修“人物串味”
适用场景：主角、男主、配角说话做事像一个人。

调用顺序：
1. 人物专属动作签名：先区分身体反应。
2. 人物专属台词签名：再区分说话节奏和句式。
3. 人物关系对话：确认同一个角色面对不同人时会换语气。
4. 情绪动作表达：让不同人物的情绪落点也不同。
5. 正文语言风格：删掉作者代言式句子。

### 示例四：修“感情线不动人”
适用场景：男女主有互动，但没有张力或暧昧层次。

调用顺序：
1. 人物关系对话：先明确关系阶段、潜台词和边界。
2. 人物专属台词签名：避免两人说话都像作者。
3. 情绪动作表达：把在意、躲闪、停顿、照顾写出来。
4. 场景描写：让环境协助拉升气氛，比如雨夜、路途、灶前、屋檐下。
5. 正文语言风格：避免把暧昧写成直白说明。

### 示例五：开书工作流
适用场景：从零开始写一本网文。

顺序建议：
1. 先用总控skill判断当前阶段：设定期 / 开篇期 / 连载期 / 修稿期。
2. 先基于当次大纲分析，整理当前应有的卷划分、章节组块与推进节奏，不机械绑定固定章数。
3. 设定期：主用人物专属动作签名、人物专属台词签名、人物关系对话。
4. 开篇期：主用正文语言风格、场景描写、情绪动作表达。
5. 连载期：按每章问题动态调用，始终以正文语言风格做统一收束。
6. 修稿期：先修关系和人物，再修场景和句子，最后统一文风。
7. 每章完成后，用“章节验收与连续性校验”确认是否符合当前规则、是否按大纲前进、是否出现回退和重复。

## 章节执行SOP

拿到一章正文后，按以下顺序检查：
1. 这一章是不是像小说，而不是提纲扩写？
2. 场景有没有在施加压力或提供安稳？
3. 情绪有没有通过动作落地？
4. 主要人物动作是否串味？
5. 主要人物台词是否串味？
6. 人物之间的关系是否能从对话中听出来？
7. 章尾是否具有继续阅读的牵引力？

## 常见总控错误

### 错误1：一上来只修句子
修正：先看结构、场景、人物、关系，再修句子。

### 错误2：每个skill都平均使用
修正：根据问题类型决定主skill和辅skill，不要机械套流程。

### 错误3：局部写得漂亮，整体文风却散
修正：最终总是回到“正文语言风格”做统一收束。

## 批量修订与交付SOP

当任务属于补字、全书复核、批量重写、格式统一时，额外执行下面流程：

1. 先读取用户当前这一次下达的硬规则。
2. 若项目目录内存在作品定位、章节目录、排版规范、进度记录，先读这些文件。
3. 默认把 `.docx` 章节文件视为正文源文件。
4. 批量任务开始前，先在进度记录中写明任务、范围、开始时间、执行要求。
5. 若用户对“没有可见进度”的工作方式敏感，优先改为小批次执行，不要只开长后台任务。
6. 每修改完一个文件，立刻更新进度记录；不能只口头说“正在处理”。
7. 每批结束后，必须汇报本批改了哪些章节、哪些未改、改前字数、改后字数，以及是否达标。

## Word文档交付要求

- 小说正文正式交付时，默认输出为真实 Word 文档，优先 `.docx`。
- 小说框架 / 大纲类文件正式交付时，也统一采用真实 Word 文档，优先 `.docx`。
- 禁止使用 HTML 伪装 `.doc` 作为最终正文交付格式。
- 若需要兼容 Word 排版，必须明确执行：标题黑体三号居中、正文宋体小四、首行缩进 2 字符、固定 29 磅行距（可接受 28—30 磅）、段前段后 0 磅、页边距上 2.54 厘米下 2.54 厘米左 2.8 厘米右 2.6 厘米，章节标题统一为“第X章 XXXXX”。
- 若用户要求统一格式，默认只改版式，不擅自改正文内容。

## 输出要求

最终输出应做到：
- 文风统一
- 场景有作用
- 情绪可见
- 人物可分
- 对话有关系张力
- 章节具备网文连载可读性

## 备注

如果任务是完整写作而不是单点修订，默认把“正文语言风格”作为总基线，再按问题需要调用其余5个skill。

## 正文基本信息要求

- 章节标题格式统一为：`第X章 XXXXX`。
- 章节规划与阶段划分，优先按当次大纲分析自由总结，不机械锁死固定章数。
- 每章目标 3200—3800 字，任何一章最低不低于 3200 字。
- 默认只强制修改低于 3200 字的章节；若用户要求全量统一，再处理已达标章节。
- 字数统计默认只算正文，不算标题。
- 如果补写后超出目标区间，应回调到目标区间内。
- 段落以短段为主，单段建议控制在 2～3 行，避免整页大段。
- 正文中不得出现空格异常、乱码、广告、外链。
- 内容补写必须补有效剧情、动作、对话、判断和后果，禁止模板化凑字、重复段落、重复表意、同义反复硬拉长度。
- 内容禁忌：
  - 不涉政
  - 不涉黄
  - 不涉暴
  - 不写过于惊悚的灵异鬼怪与封建迷信
  - 不抹黑现实人物与现实职业
